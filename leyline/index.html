Leyline · a code map for coding agents

A map of your codebase for you and your agents.

There are good tools for asking questions about code, mapping it, writing specs and reviewing pull requests, and several of them now check an agent's work against a spec. This page explains why I built Leyline anyway, and where the other tools do better.

Other tools do this

Other tools already do most of what Leyline does.

Leyline is a tool you install beside a coding agent. It maps a codebase into a graph, assists with human understanding, helps the agent plan a change as a spec, coordinates agent reviews against the plan, and then checks the finished code against the spec using the graph and your test results. 

Each of those jobs already has a good tool. Sourcegraph Deep Search answers questions about a codebase and cites the files and searches it used. Local graph servers such as GitNexus, codebase-memory-mcp and code-review-graph give an agent a code graph over MCP. OpenSpec (which Leyline builds on), Spec Kit and Kiro turn a request into a spec. CodeRabbit, Greptile and Qodo review pull requests, and CodeScene reads change coupling out of git history more thoroughly than Leyline does.

Several of them now check an agent's work against the spec as well. OpenSpec has /opsx:verify, Spec Kit has /speckit.converge, and Kiro runs property-based tests built from the requirements. So it's fair to ask why Leyline should exist.

The matrix below comes from a research pass against vendor docs and READMEs on 2026-10-07. Hover or tap a cell to see what the tools in that row do in that phase, with a source where I have one.

Every other row has gaps. Leyline covers every phase, but covering a phase doesn't make it the best tool there, and "When another tool is the better choice" below says where it isn't. The case for using it rests on four differences, which the rest of this page takes one at a time: 1) no model judges the work, 2) one map shares decisions between steps, 3) the records stay in your repository, 4) and the tool says what it doesn't know.

Reason 1 · the verdict

Most checkers ask a model whether a model did the work.

/opsx:verify has a language model search the code for evidence of each task and scenario, then report CRITICAL, WARNING and SUGGESTION items that don't block archiving. /speckit.converge has a model read the source against the spec, plan and tasks, and it treats ticks already in the task list as unverified claims, a choice I agree with. Qodo rates each ticket Fully, Partially or Not compliant, and CodeRabbit marks linked issues Addressed, Not addressed or Unclear. All four are a model's verdict, and none of them uses test results.

Kiro is the exception. It turns requirements into property-based tests, links each to its requirement and task, and runs them. It doesn't check whether each task was done against a diff of the code.

A model that judges an agent's work reads the agent's explanation, and agents write fluent explanations easily. Leyline has no language model in it. A task's verdict comes from what changed on the graph between the plan and now. A scenario's verdict comes from its test's result before and after the change, and whether that test ran the changed code. Leyline also lists every edit that falls outside the spec, which I didn't find in any other tool.

Every engineer knows the difference between a pull request's description and its CI run. A well-written description can talk a reviewer into approving a change. It can't make a failing test pass. Asking a model whether an agent did the work is like reviewing the description: the agent's report is one of the things being judged, and agents write convincing reports easily. Leyline's verdict works like CI. It reads what changed in the code and what the tests did, and the report isn't one of its inputs.

Agent-first, with no model inside

The agent does the writing, and Leyline checks it against evidence.

A fair objection is that a tool with no language model in it can't be built for agents. It can, because the agent does all the language work. It drafts the spec, explains code, plays the logic and performance reviewers, and writes the code. Leyline gives it facts, in answers kept short enough for its context (about 24,000 characters for most tools, up to 36,000 for the few that walk code, with a note on what was cut and how to see the rest), and it ends every step with a Next: line. The chain of Next: lines is the workflow.

The person makes the decisions. Only the person resolves a finding, and a rule an agent adds stays "suggested" until the person confirms it.

Reason 2 · one map

Separate tools don't share decisions from one step to the next.

Suppose you use a chat tool to understand the code, a spec tool to plan, a review bot on the pull request and something else to check the result. Each step starts from its own view of the code, and each decision stays in the tool that made it. Leyline keeps one map and one store of findings, so each step starts from what the previous one decided.

Your own change usually starts spec-first, with a plan, and someone else's branch starts at the pull-request review. Both ways in write findings into the same store, and later changes read them back. Scroll through the steps, or use the buttons, to see what each step passes to the next.

1 · Understand → PlanThe names in the spec are names on the map. Code in backticks in tasks.md is looked up, and a name that isn't on the map is read as new code.
2 · Plan → Review the planThe plan page says what will be written, what must be edited with it, what it reaches, and which code shares a caller, a field or a commit history with it while no task names it. The reviewers start from those facts.
3 · Review the planEach reviewer's facts open with the past decisions that apply to this code, closest first. Only the person resolves a finding, and a rejection with a reason becomes a learning.
4 · ImplementThe first plan took a snapshot of the code. If the spec changes halfway, the comparison still starts from the code as it was when the change was planned.
5 · Checkcheck compares the code with that snapshot and the tests with the run recorded at plan time. A tick in tasks.md never counts, and the command exits 0 only when the change was done as agreed.
6 · Review the pull request (the second way in)A branch with no spec gets leyline pr, which reads the change from the code: what changed, callers of a changed signature that weren't edited, removed code that's still called, and changed code no test reaches. Its findings go in the same store, and with --gate it exits 1 while something the map can show is broken is left, so it can hold a merge in CI the way check holds a change.
7 · Re-review after new commitsRunning it again shows what changed since the last review, and marks each open finding "may be fixed" or "still applies". Running it on unchanged code changes nothing.
8 · The next changeThe next plan lists earlier changes and reviews that touched the same code, and its reviewers read the learnings first. drift lists code the living specs name that has since gone, moved or changed signature.

One finding, across two changes

The clearest example is a finding that comes back in a later change. In the loud-engine plan, Leyline noted that Engine.name is also used by Engine.child. A logic reviewer turned that into a finding. The person rejected it and gave a reason, and Leyline kept the reason as a learning. When a later change raised the same worry, the plan page said so. Step through it below.

Reason 3 · files you commit

The spec, the page and the decisions live in your repository.

Specs are OpenSpec markdown. The page for each change, leyline.md, sits in that change's folder. Learnings are a JSON file with sorted keys, one entry per decision, each holding the reason in the person's own words. A learning is retired automatically once people have accepted at least two of the findings it matched, and more than they rejected. You can read all of it in a diff and review it like code.

The review bots keep this kind of memory elsewhere. CodeRabbit stores learnings on its servers by git organization; they never expire, and admins can edit them. Copilot Memory (in preview) cites code locations, checks each memory against the current branch before using it, and deletes a memory after 28 days without use. Those are reasonable designs for a hosted service. Leyline runs on your machine, needs no account, and is licensed under the GPL, version 3. Its MCP tools read and write only inside the repositories it maps, and it refuses a .leyline/ folder that a repository commits, so a pull request can't hand it a ready-made map.

Reason 4 · measured

Every link records how it was found, and the accuracy is published.

Every record on the map belongs to one of three layers. Facts come from the source and are rebuilt on every index. A model (in practice, your agent) writes inferred records, with evidence and a confidence, and Leyline flags them as stale when the code behind the evidence changes. Intent is what you state, such as rules and boundaries.

Links between functions come in three grades. A compiler confirmed an exact link, using Roslyn for C# or a SCIP index for other languages. Leyline worked out a heuristic link from the syntax, and made a guess by name alone because only one declaration had that name. The map page draws them solid, dashed and dotted, and answers carry the same grade.

Two of the five verdicts let Leyline decline to answer. "Inconclusive" means the map can't place the code or no result was recorded. "Needs a person" means a task names no code, or a test passed without Leyline being able to show it ran the changed code.

Polly's fluent API has up to twenty overloads per name, which is the hard case for linking by syntax. Its packages couldn't be restored, so the compiler binds only part of the code, and on that part the compiler pass confirmed 4,844 of the syntax links and removed 1,286, nearly all of them extra overloads of the right method.

The third number is about learnings. A finding about trimming the name in Engine.child shares code with the rejected upper-casing finding, but it's a different worry, and it scored 0.44 against a threshold of 0.45. I think leaving it unmarked was the right call. When a past decision might not apply, I'd rather Leyline miss the match than put the wrong reason in front of the person.

Where it loses

When another tool is the better choice.

  • History analysis. Leyline finds files and functions that usually change together. CodeScene goes much further, with coupling by commit, author and time window, or by ticket, and it has an MCP server too.
  • Tests generated from requirements. Leyline marks a scenario that says "for any", "always" or "never" as one a property test fits, and names the library for its language. It doesn't write the test, and Kiro does.
  • A spec that's wrong. Leyline checks the code against the spec, so it can't tell you the spec asks for the wrong thing. The real agent above caught a case of this. The spec never said whether shout upper-cases the name, and the agent raised it as a decision for the person. Leyline reported nothing about it. Finding gaps in the spec is the reviewers' job.
  • Language depth. C#, Python and TypeScript have hand-written adapters that see receiver types, overloads, field reads and writes, events and routes. Every other language goes through a generic adapter, unless you provide a SCIP index from the language's own indexer.
Try it

Three commands to set up, and then you ask your agent.

pip install leyline-code                  # Python 3.10+
claude mcp add leyline -- leyline serve   # connect Claude Code
leyline skills install                    # into this repo; --to ~ for every project

Then ask in plain words: "Plan adding an export button, with tests," or "Review pull request 123." The agent maps the code when it needs to. Every command also works by hand.
